# 1. 프롬 이모티콘 정산 (Master Admin)

## 1.1 개요

| 항목 | 내용 |
|---|---|
| 서비스 | 프롬(fromm) — K-pop 아티스트-팬 프라이빗 메시지 구독 앱 |
| 기간 | 2026.07 ~ 2026.10 (구축 후 운영·정산 대응 지속) |
| 역할 | 기획 단독 담당 — 요구사항 정리, PRD(v5), 정책정의서(v6), 와이어프레임, 정산서 양식, 운영 가이드, Jira 티켓, 운영 대응 |
| 협업 | PM 리드 / 백엔드 2 / 프론트 1 / 디자인 1 / QA 1 / 운영 3 / 외부 정산 그룹웨어 담당 |
| 사용 도구 | Figma, Jira, Slack, Excel(정산서 검증), PDF 정산서 |

## 1.2 배경 및 문제

- 기존 정산 시스템은 **메시지 구독 정산만** 지원. 이모티콘 매출은 시스템 밖에서 수기 처리
- 문제를 3가지로 정의
  1. **수기 처리 비효율** — 이모티콘 정산을 엑셀로 별도 계산·발행
  2. **시스템 확장성 부재** — 정산정책·계약·정산서 구조가 메시지 단일 서비스 기준
  3. **소속사 불편** — 파트너센터에서 이모티콘 정산 내역 확인 불가
- 핵심 난제: 선급금이 **서비스 구분 없이 계좌 단위**로 관리되고 있어, 메시지·이모티콘이 같은 선급금을 나눠 쓸 때 **이중 차감·차감 순서 꼬임** 위험

## 1.3 담당 범위

- 사전 확인 안건 정리 및 의사결정 미팅 주도
  - 매출 산정 방식(1개월권 반복구독 여부, 매출 인식 시점), 그룹/개인 이모티콘 구분, 정산방식·계좌·요율의 메시지 동일 여부, 백오피스 이관 범위
- 통합 정산(방식 A) vs 분리 정산(방식 B)을 PRD 전 섹션에 걸쳐 병렬 비교 → 의사결정 후 바로 개발 요청 가능한 구조로 작성
- 정책정의서: 정산방식별 계산식, 선급금 처리, 검증 공식, 권한, 예외 케이스
- 파트너센터 와이어프레임(Figma), 정산서 엑셀/PDF 양식
- 운영 가이드, Jira 티켓, 운영팀·개발팀 커뮤니케이션

## 1.4 핵심 의사결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 정산서 발행 단위 | 메시지·이모티콘 **분리 발행** | 소속사별 정산방식 상이 가능성, 기존 메시지 정산 사이드이펙트 최소화 |
| 정산 단위 | 이모티콘 팩 단위 | 그룹/개인 이모티콘 혼재 대응 |

| 큐 라이프사이클 | 승인 즉시 큐에서 제거 → 완료 이력으로 이관 | 승인 대기 / 완료 이력 2섹션 UI와 일치 |

| 구독수 집계 | 일별 재계산 → **스냅샷 방식** (7/1 적용) | 과거 수치가 사후 변경되는 문제 제거 |
| 계산식 | 제반비용 차감 → 순매출 → 수익분배율 → VAT 처리 → 세금 | 정산방식(현금_개인/법인, 선급_개인/법인)별로 확정 |
| 조정금액 API | 음수 허용, 사유(description) 필드 추가 | 추가정산·추가비용·소급 반영을 하나의 기능으로 처리 |

## 1.5 문제 해결 사례

### ① 선급금 공유 문제 → 큐 구조 설계
- **상황**: 메시지·이모티콘 정산서가 같은 계좌의 선급금을 차감. 발행 순서에 따라 잔액이 달라지고, 동시 발행 시 이중 차감 가능
- **행동**: 계좌당 큐 1개로 정산서 순서를 시스템이 관리하도록 설계. 메시지 우선 차감, 승인 시 큐에서 즉시 제거, 중간 삭제 시 하위만 재계산하는 규칙 정의
- **결과**: 선급금 차감 순서가 운영자 판단이 아닌 시스템 규칙으로 고정

### ② 계산 로직 역산 검증
- **상황**: 세금 계산 로직을 추정으로 작성했다가 실제 발행 정산서와 불일치
- **행동**: 실제 발행 정산서·DB 조회 결과로 역산 검증 → 세금 절사 기준(원 단위 절사), 선급 잔액이 충분해도 세금 적용됨 등을 확인 후 정책 확정
- **결과**: 이후 계산 규칙은 "샘플 케이스 역산 검증 후 문서화"를 원칙으로 운영

### ③ 운영 중 정산 오류 발견·원인 규명
| 오류 | 원인 | 조치 |
|---|---|---|
| 통계 중복 집계 | 계약 기간 중복 등록 허용 | 계약 기간 중복 검증 정책 추가 |
| 정산서 하단 문구 오류 | 선급 개인/법인 통합 정책에서 잔액 소진 케이스 미정의 | 잔액 소진 케이스 문구 정책 보완 |
| 파트너센터 이모티콘 통계 누락 | 멤버 개인 그룹이 정산 제외 플래그로 필터링됨 | "부서 담당 이모티콘 팩 기준" 집계로 수정 방향 확정 |
| 정산금 과다 지급 (7~8월 약 +9.3%) | 정산 제외 굿즈(무료체험) 테이블 등록 누락 | 원인 규명 및 제외 대상 등록 `[확인 필요: 회수/차감 처리 결과]` |
| 3분기 정산서 VAT 과다 반영 (약 68,121원) | VAT 포함 환산 금액이 VAT 별도 줄에 중복 가산 | 오류 지점 특정 `[확인 필요: 정정 처리 결과]` |

### ④ 2분기 누락분 소급 정산
- 2분기 이모티콘 정산 누락 아티스트분을 조정금액 기능으로 소급 반영
- 아티스트 4인 2분기 개별 정산서를 기존 선급 양식 기반으로 제작 — 정산기간·레이아웃 수정, VAT 별도 금액은 반올림 없이 정확한 값으로 반영해 최종 PDF 발행

## 1.7 어필 포인트

- 단순 기능 추가가 아니라 **기존 정산 구조(계좌 단위 선급금)의 숨은 충돌**을 먼저 찾아 시스템 구조로 해결
- 정산 계산은 **실제 발행 정산서로 역산 검증** 후 확정 → 추정 기반 정책 배제
- 오픈 이후에도 운영 데이터를 직접 대조해 **과다 지급·VAT 중복 등 금전 오류를 기획자가 먼저 발견**
- 운영팀(평문 안내)·개발팀(기술 질문)·외부 그룹웨어 담당까지 대상별 커뮤니케이션

## 2-1. 사용자 주문 · PG 연동

### 배경 및 문제
- 한국 PG와 다른 일본 결제 생태계: 편의점 결제(승인=입금 완료), 지정매입, 결제수단별 개별 심사, 특정상거래법 등 법적 표기 의무
- PG 계약·심사·연동을 **기획자가 직접 일본어 문서를 읽고** 리드해야 하는 상황

### 담당 범위
- 결제수단별 결제 프로세스 정의 (승인 → 매입 → 환불/취소)
- 주문·결제·상품·배송 **4개 레이어 상태값 체계** 정의 및 연동 규칙 정리
- SBPS 결제수단별 심사 일정·의존성 관리 및 일본어 커뮤니케이션
- PayPay 결제수단 추가 PRD·정책정의서 작성
- 운영환경 결제 테스트 체계 (IP 화이트리스트, 웹훅, 현지 테스트 대행)

### 결제수단별 프로세스 정의
| 결제수단 | 프로세스 | 특이사항 |
|---|---|---|
| 신용카드 | 승인 → 매입 → paid | 최소 결제 2엔 (잔여 1엔 시 재결제 불가). 카드사 룰 변경(9/1)으로 매입 방식 재정비 |
| 편의점 | 번호 발급 → 고객 편의점 입금 → paid | 승인·매입 분리 없음. 환불 API 없음 → 수동 송금 |
| PayPay | QR 결제 → 자동 매입 → paid | 링크형도 별도 API로 부분환불 가능, 환불 기한·횟수 제약 |
| 메루페이 | SBPS 연동 | 오픈 완료 |

### 핵심 의사결정 / 문제 해결

**① PayPay PRD의 정책 오류 2건 사전 차단**
- 상황: 기존 PRD에 "링크형 PayPay는 부분환불 불가", "배송준비 시점 지정매입" 가정이 들어가 있었음
- 행동: SBPS 공식 스펙 직독 + 최신 신용카드 정책과 교차 검증
  - 링크형 여부와 무관하게 **환불은 별도 API로 부분환불 가능**
  - 카드가 9/1 카드사 룰 변경으로 이미 자동매입 + 통합 환불 API 구조로 이동 → PayPay도 동일 구조로 정렬
- 결과: 개발 착수 전 정책 수정 → 결제수단 간 환불 구조 일원화, 불필요한 분기 개발 방지

**② PayPay 에러 케이스 정의**
- 카드 공통 인라인·토스트 에러 공유, 편의점 전용 계좌 검증 제외
- PayPay 전용 인라인 에러 2종(환불 기한 초과, 환불 횟수 한도) 추가

**③ 한국에서 테스트 불가능한 결제수단 QA**
- 한국에서 PayPay 앱 사용 불가 → SBPS 웹 테스트 계정 + **일본 현지 앱 결제 테스트 대행 요청**
- IP 화이트리스트 상호 등록, 웹훅 URL 설정

**④ 세븐일레븐 편의점 심사 대응**
- 지적사항: 특정상거래법 상세 링크 미설정, 배송비 표기 위치(장바구니 담기 전 상품페이지 노출 필요), 교환/환불 안내 일본어 병기
- 사용자 화면 수정 요건 정리 후 대응. 심사가 중단·취소 처리되어 **재심사 시 신규 심사(약 2개월)** 필요함을 확인하고 일정 재수립
- 이코넥스트 수수료 인상(2026.11.1부터 전 구간 +20엔) 공지 대응 `[확인 필요: 반영 결과]`

### 산출물
- PayPay PRD (사용자 영역 / 백오피스 영역 분리) + 정책정의서 (별도 문서)
- 결제수단별 프로세스·상태값 체계 문서
- SBPS 일본어 커뮤니케이션 (번역 + 한국어 요약표 병행)

### 성과

## 2-2. 백오피스 주문 · 환불

### 배경 및 문제
- 최초 백오피스는 **편의점 환불 전용**으로 구축 → 신용카드 주문까지 포함한 **전체 주문 관리 백오피스**로 확장 필요 (PRD 작성 2026.06.09)
- 결제수단마다 환불 방식이 근본적으로 다름

| 항목 | 신용카드 | 편의점 |
|---|---|---|
| 환불 API | SBPS 환불 API | 없음 |
| 처리 방식 | 시스템 자동 | CS 수동 계좌 송금 |
| 계좌 정보 | 불필요 | 필수 (젠데스크 경유) |
| 본인 확인 | 불필요 | 필수 |
| 완료 기준 | API 성공 응답 | CS 환불 완료 버튼 |

### 담당 범위
- 주문 목록 / 주문 상세(환불 처리) / 환불 이력(PG 대사용 엑셀) 화면 기획
- 환불 유형(전체 / 부분 / 금액만) 정책 및 API 분기 설계
- 결제수단별 고객 마이페이지 상태 노출 정의
- 예외·오류 처리 기준, QA 대응, CS 운영 가이드, 릴리즈 노트

### 핵심 정책
- 환불 가능 상태: 상품 상태가 결제 완료(paid)인 건에 한함
- 환불 가능 금액: PG 결제금액 − 기환불금액 이내
- 편의점 수수료: 상품금액 기준 1회만 산정 (수수료 포함 총액 기준 재산정 불가)
- 패키지 굿즈: 패키지 단위로만 환불 (서브굿즈 개별 환불 불가)
- 편의점 미입금 건: 입금 기한 초과 시 전체 취소만 가능
- 환불 완료 후 상태 복구 불가
- 갤럭시 신규 상태값: 환불 처리 중(refund_pending), 환불 반려(refund_rejected)

### 문제 해결 사례

**① 환불 유형을 명시적 API 분기로 재설계**
- 상황: 상품 미선택 환불 요청이 "전체 취소"와 "금액 조정" 두 의도를 구분 없이 처리 → **주문 취소금액과 상품별 취소금액 합계가 어긋나는 문제**
- 행동: 전체 / 부분 / 금액만 환불을 API 레벨에서 명시적으로 분기
- 결과: 주문 금액과 상품별 금액의 정합성 확보

**② 환불 금액 공식 버그 수정**
- 환불 가능 금액 계산에서 **기환불 수수료 누락** 발견 → 공식 수정

**③ 기존 코드 실동작 분석으로 정책 확정**
- 프롬 기존 환불 로직의 실제 동작을 분석해 전체/부분환불 적용 조건, 배송 상태별 환불 유형 제약, 귀책 여부별 처리 기준 확정
- QA 문의("부분환불로 전 상품 처리 시 주문이 취소로 자동 마감") → 프롬 정책과 동일한 정상 동작임을 근거와 함께 회신

**④ 엣지케이스 정의**
- 0엔 상품 환불 차단
- 신용카드 잔여 1엔 케이스 차단 (최소 결제 2엔 제약)
- 결제 정보 미생성(처리 중) 상태 별도 처리
- 매입 대기 상태에서 환불 요청 시 경고 배너 + CS 판단
- 이미 환불 처리 중인 상품 재선택 불가, 2FA 코드 오류, 본인 확인 불일치 시 메모 필수

**⑤ 고객 상태 노출 설계**
- 신용카드: 승인 버튼 → API 즉시 호출 → 성공 시 전 상태 일괄 변경 (주문 완료 → 취소 완료 / 부분 취소 완료). 실패 시 상태 변경 없이 토스트, CS 재시도
- 편의점: 2단계 — 승인 시 처리 중 상태 → CS 실제 송금 후 환불 완료 버튼 시점에 최종 변경. 송금 실패 시 처리 중 유지 + 젠데스크로 계좌 재확인

### 산출물
- 주문 관리 백오피스 PRD (편의점 환불 PRD 확장)
- 환불 정책·예외 처리 기준, 결제수단별 상태 전이표
- 백오피스 CS 운영 가이드 v1.0
- 주문/취소 프로젝트 릴리즈 노트
- 테크블로그 아티클 + 브런치 2편 (한국 PG와의 차이, 해결 방법, 개선 방향)

### 어필 포인트 (2-1, 2-2 공통)
- 비전공 기획자로서 **일본어 PG 스펙을 직접 읽고** 정책 오류를 개발 전에 차단
- 결제수단마다 다른 환불 구조(API 자동 vs 수동 송금)를 하나의 백오피스 흐름으로 통합
- 법적 심사(특정상거래법)·PG 심사·현지 테스트까지 **기술 외 리스크**를 일정에 반영
- 경험을 사내 테크블로그로 문서화해 조직 지식으로 전환

# 이력서 문장 초안

- **[이모티콘 정산]** 메시지 단일 정산 체계에 이모티콘 정산 편입 기획 — 계좌 단위 선급금 공유로 인한 이중 차감 위험을 계좌당 큐 구조로 해결하고, 정산 계산식을 실제 정산서 역산으로 검증 후 확정
- **[이모티콘 정산]** 오픈 후 운영 데이터 대조로 정산 제외 상품 누락(7~8월 약 9.3% 과다 지급), VAT 중복 가산 등 금전 오류의 원인 규명 및 수정 방향 수립
- **[갤럭시 PG]** 일본 PG(SBPS) 연동 결제 파트 PM — 신용카드·편의점·PayPay·메루페이 연동, 일본 특정상거래법 심사 대응, SBPS 스펙 직독으로 PayPay 환불 정책 오류 2건 개발 전 정정
- **[갤럭시 백오피스]** 편의점 전용 환불 백오피스를 전 결제수단 주문 관리로 확장 — 전체/부분/금액만 환불 API 분기 설계로 주문-상품 금액 불일치 해소, 환불 금액 공식 버그 수정, CS 운영 가이드 작성
- **[알림음]** 10/26 운영 반영 마감에 맞춰 스토어 심사 일정을 역산해 PRD·정책·화면설계 작성, 화면-정책 대조로 불일치 5건 사전 수정
