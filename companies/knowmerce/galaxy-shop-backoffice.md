## 배경 및 문제
- 최초 백오피스는 **편의점 환불 전용**으로 구축 → 신용카드 주문까지 포함한 **전체 주문 관리 백오피스**로 확장 필요 (PRD 작성 2026.06.09)
- 결제수단마다 환불 방식이 근본적으로 다름

| 항목 | 신용카드 | 편의점 |
|---|---|---|
| 환불 API | SBPS 환불 API | 없음 |
| 처리 방식 | 시스템 자동 | CS 수동 계좌 송금 |
| 계좌 정보 | 불필요 | 필수 (젠데스크 경유) |
| 본인 확인 | 불필요 | 필수 |
| 완료 기준 | API 성공 응답 | CS 환불 완료 버튼 |

## 담당 범위
- 주문 목록 / 주문 상세(환불 처리) / 환불 이력(PG 대사용 엑셀) 화면 기획
- 환불 유형(전체 / 부분 / 금액만) 정책 및 API 분기 설계
- 결제수단별 고객 마이페이지 상태 노출 정의
- 예외·오류 처리 기준, QA 대응, CS 운영 가이드, 릴리즈 노트

## 핵심 정책
- 환불 가능 상태: 상품 상태가 결제 완료(paid)인 건에 한함
- 환불 가능 금액: PG 결제금액 − 기환불금액 이내
- 편의점 수수료: 상품금액 기준 1회만 산정 (수수료 포함 총액 기준 재산정 불가)
- 패키지 굿즈: 패키지 단위로만 환불 (서브굿즈 개별 환불 불가)
- 편의점 미입금 건: 입금 기한 초과 시 전체 취소만 가능
- 환불 완료 후 상태 복구 불가
- 갤럭시 신규 상태값: 환불 처리 중(refund_pending), 환불 반려(refund_rejected)

## 문제 해결 사례

**① 환불 유형을 명시적 API 분기로 재설계**
- 상황: 상품 미선택 환불 요청이 "전체 취소"와 "금액 조정" 두 의도를 구분 없이 처리 → **주문 취소금액과 상품별 취소금액 합계가 어긋나는 문제**
- 행동: 전체 / 부분 / 금액만 환불을 API 레벨에서 명시적으로 분기
- 결과: 주문 금액과 상품별 금액의 정합성 확보

**② 환불 금액 공식 버그 수정**
- 환불 가능 금액 계산에서 **기환불 수수료 누락** 발견 → 공식 수정

**③ 기존 코드 실동작 분석으로 정책 확정**
- 프롬 기존 환불 로직의 실제 동작을 분석해 전체/부분환불 적용 조건, 배송 상태별 환불 유형 제약, 귀책 여부별 처리 기준 확정
- QA 문의("부분환불로 전 상품 처리 시 주문이 취소로 자동 마감") → 코드 분석으로 정상 동작 확인 후 백엔드 담당자에게 이중 확인, 근거와 함께 회신
  - 확정 정책: 주문상세 전 상품값 환불 완료(미취소 상품 수 = 0) 시 **배송비 잔존 여부와 무관하게** 주문 상태 Cancelled 전환 — 부분취소(CancelledPartial)는 미환불 상품이 남아있을 때만 유지
  - CS 담당자 향 회신 문구 내가 직접 작성 후 전달

**④ 엣지케이스 정의**
- 0엔 상품 환불 차단
- 신용카드 잔여 1엔 케이스 차단 (최소 결제 2엔 제약)
- 결제 정보 미생성(처리 중) 상태 별도 처리
- 매입 대기 상태에서 환불 요청 시 경고 배너 + CS 판단
- 이미 환불 처리 중인 상품 재선택 불가, 2FA 코드 오류, 본인 확인 불일치 시 메모 필수

**⑤ 고객 상태 노출 설계**
- 신용카드: 승인 버튼 → API 즉시 호출 → 성공 시 전 상태 일괄 변경 (주문 완료 → 취소 완료 / 부분 취소 완료). 실패 시 상태 변경 없이 토스트, CS 재시도
- 편의점: 2단계 — 승인 시 처리 중 상태 → CS 실제 송금 후 환불 완료 버튼 시점에 최종 변경. 송금 실패 시 처리 중 유지 + 젠데스크로 계좌 재확인
