## 배경 및 문제

- 기존 정산 시스템은 **메시지 구독 정산만** 지원. 이모티콘 매출은 시스템 밖에서 수기 처리
- 문제를 3가지로 정의
  1. **수기 처리 비효율** — 이모티콘 정산을 엑셀로 별도 계산·발행
  2. **시스템 확장성 부재** — 정산정책·계약·정산서 구조가 메시지 단일 서비스 기준
  3. **소속사 불편** — 파트너센터에서 이모티콘 정산 내역 확인 불가
- 핵심 난제: 선급금이 **서비스 구분 없이 계좌 단위**로 관리되고 있어, 메시지·이모티콘이 같은 선급금을 나눠 쓸 때 **이중 차감·차감 순서 꼬임** 위험

## 담당 범위

- 사전 확인 안건 정리 및 의사결정 미팅 주도
  - 매출 산정 방식(1개월권 반복구독 여부, 매출 인식 시점), 그룹/개인 이모티콘 구분, 정산방식·계좌·요율의 메시지 동일 여부, 백오피스 이관 범위
- 통합 정산(방식 A) vs 분리 정산(방식 B)을 PRD 전 섹션에 걸쳐 병렬 비교 → 의사결정 후 바로 개발 요청 가능한 구조로 작성
- 정책정의서: 정산방식별 계산식, 선급금 처리, 검증 공식, 권한, 예외 케이스
- 파트너센터 와이어프레임(Figma), 정산서 엑셀/PDF 양식
- 운영 가이드, Jira 티켓, 운영팀·개발팀 커뮤니케이션

| 항목 | 결정 | 근거 |

| 큐 라이프사이클 | 승인 즉시 큐에서 제거 → 완료 이력으로 이관 | 승인 대기 / 완료 이력 2섹션 UI와 일치 |
| 큐 삭제 정책 | 중간 항목 삭제 시 하위 항목만 재계산 (전체 재생성 X) | 연산 범위 최소화, 기승인 건 보호 |

| 계산식 | 제반비용 차감 → 순매출 → 수익분배율 → VAT 처리 → 세금 | 정산방식(현금_개인/법인, 선급_개인/법인)별로 확정 |
| 조정금액 API | 음수 허용, 사유(description) 필드 추가 | 추가정산·추가비용·소급 반영을 하나의 기능으로 처리 |

## 문제 해결 사례

### ① 선급금 공유 문제 → 큐 구조 설계
- **상황**: 메시지·이모티콘 정산서가 같은 계좌의 선급금을 차감. 발행 순서에 따라 잔액이 달라지고, 동시 발행 시 이중 차감 가능
- **행동**: 계좌당 큐 1개로 정산서 순서를 시스템이 관리하도록 설계. 메시지 우선 차감, 승인 시 큐에서 즉시 제거, 중간 삭제 시 하위만 재계산하는 규칙 정의
- **결과**: 선급금 차감 순서가 운영자 판단이 아닌 시스템 규칙으로 고정

### ② 계산 로직 역산 검증
- **상황**: 세금 계산 로직을 추정으로 작성했다가 실제 발행 정산서와 불일치
- **행동**: 실제 발행 정산서·DB 조회 결과로 역산 검증 → 세금 절사 기준(원 단위 절사), 선급 잔액이 충분해도 세금 적용됨 등을 확인 후 정책 확정
- **결과**: 이후 계산 규칙은 "샘플 케이스 역산 검증 후 문서화"를 원칙으로 운영

### ③ 운영 중 정산 오류 발견·원인 규명
| 오류 | 원인 | 조치 |
|---|---|---|
| 통계 중복 집계 | 계약 기간 중복 등록 허용 | 계약 기간 중복 검증 정책 추가 |
| 정산서 하단 문구 오류 | 선급 개인/법인 통합 정책에서 잔액 소진 케이스 미정의 | 잔액 소진 케이스 문구 정책 보완 |
| 파트너센터 이모티콘 통계 누락 | 멤버 개인 그룹이 정산 제외 플래그로 필터링됨 | "부서 담당 이모티콘 팩 기준" 집계로 수정 방향 확정 |
| 정산금 과다 지급 (7~8월 약 +9.3%) | 정산 제외 굿즈(무료체험) 테이블 등록 누락 | 원인 규명 및 제외 대상 등록 `[확인 필요: 회수/차감 처리 결과]` |
| 3분기 정산서 VAT 과다 반영 (약 68,121원) | VAT 포함 환산 금액이 VAT 별도 줄에 중복 가산 | 오류 지점 특정 `[확인 필요: 정정 처리 결과]` |

### ④ 2분기 누락분 소급 정산
- 2분기 이모티콘 정산 누락 아티스트분을 조정금액 기능으로 소급 반영
- 아티스트 4인 2분기 개별 정산서를 기존 선급 양식 기반으로 제작 — 정산기간·레이아웃 수정, VAT 별도 금액은 반올림 없이 정확한 값으로 반영해 최종 PDF 발행

## 어필 포인트

- 단순 기능 추가가 아니라 **기존 정산 구조(계좌 단위 선급금)의 숨은 충돌**을 먼저 찾아 시스템 구조로 해결
- 정산 계산은 **실제 발행 정산서로 역산 검증** 후 확정 → 추정 기반 정책 배제
- 오픈 이후에도 운영 데이터를 직접 대조해 **과다 지급·VAT 중복 등 금전 오류를 기획자가 먼저 발견**
- 운영팀(평문 안내)·개발팀(기술 질문)·외부 그룹웨어 담당까지 대상별 커뮤니케이션
