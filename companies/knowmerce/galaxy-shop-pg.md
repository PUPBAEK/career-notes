## 상세

## 배경 및 문제
- 한국 PG와 다른 일본 결제 생태계: 편의점 결제(승인=입금 완료), 지정매입, 결제수단별 개별 심사, 특정상거래법 등 법적 표기 의무
- PG 계약·심사·연동을 **기획자가 직접 일본어 문서를 읽고** 리드해야 하는 상황

## 담당 범위
- 결제수단별 결제 프로세스 정의 (승인 → 매입 → 환불/취소)
- 주문·결제·상품·배송 **4개 레이어 상태값 체계** 정의 및 연동 규칙 정리
- SBPS 결제수단별 심사 일정·의존성 관리 및 일본어 커뮤니케이션
- PayPay 결제수단 추가 PRD·정책정의서 작성
- 운영환경 결제 테스트 체계 (IP 화이트리스트, 웹훅, 현지 테스트 대행)

## 결제수단별 프로세스 정의
| 결제수단 | 프로세스 | 특이사항 |
|---|---|---|
| 신용카드 | 승인 → 매입 → paid | 최소 결제 2엔 (잔여 1엔 시 재결제 불가). 카드사 룰 변경(9/1)으로 매입 방식 재정비 |
| 편의점 | 번호 발급 → 고객 편의점 입금 → paid | 승인·매입 분리 없음. 환불 API 없음 → 수동 송금 |
| PayPay | QR 결제 → 자동 매입 → paid | 링크형도 별도 API로 부분환불 가능, 환불 기한·횟수 제약 |
| 메루페이 | SBPS 연동 | 오픈 완료 |

## 핵심 의사결정 / 문제 해결

**① PayPay PRD의 정책 오류 2건 사전 차단**
- 상황: 기존 PRD에 "링크형 PayPay는 부분환불 불가", "배송준비 시점 지정매입" 가정이 들어가 있었음
- 행동: SBPS 공식 스펙 직독 + 최신 신용카드 정책과 교차 검증
  - 링크형 여부와 무관하게 **환불은 별도 API로 부분환불 가능**
  - 카드가 9/1 카드사 룰 변경으로 이미 자동매입 + 통합 환불 API 구조로 이동 → PayPay도 동일 구조로 정렬
- 결과: 개발 착수 전 정책 수정 → 결제수단 간 환불 구조 일원화, 불필요한 분기 개발 방지

**② PayPay 에러 케이스 정의**
- 카드 공통 인라인·토스트 에러 공유, 편의점 전용 계좌 검증 제외
- PayPay 전용 인라인 에러 2종(환불 기한 초과, 환불 횟수 한도) 추가

**③ 한국에서 테스트 불가능한 결제수단 QA**
- 한국에서 PayPay 앱 사용 불가 → SBPS 웹 테스트 계정 + **일본 현지 앱 결제 테스트 대행 요청**
- IP 화이트리스트 상호 등록, 웹훅 URL 설정

**④ 세븐일레븐 편의점 심사 대응**
- 지적사항 3건: ① 특정상거래법 상세 링크 미설정(개발팀 작업 예정), ② 배송비 표기 위치(장바구니 담기 전 상품페이지 노출 필요), ③ 교환/환불 안내 일본어 병기
- 사용자 화면 수정 요건 정리 후 대응. 심사가 중단·취소 처리되어 **재심사 시 신규 심사(약 2개월)** 필요함을 확인하고 일정 재수립
- SBPS 담당자 답변 기일 재촉구에 "11월 중순 완료 예상"으로 내가 직접 회신 (일본어 커뮤니케이션)
- 이코넥스트 수수료 인상(2026.11.1부터 전 구간 +20엔) 공지 수신 → 내부 확인 후 대응 예정 `[확인 필요: 반영 결정]`
  - 영향 범위: 편의점 결제 중 FamilyMart 제외 전 브랜드(이코넥스트 망 경유)
- 결제 플로우 문서(8단계) 일본어 번역본 SBPS 담당자에게 공유 (내가 직접 번역 작성)
