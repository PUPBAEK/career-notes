# career-notes 사용 가이드

업무 대화에서 쌓인 경험이 이력서까지 가는 흐름과, 각 대화에 붙여넣을 명령어 모음.

---

## 1. 처음 한 번만 설정

1. 업무용 claude.ai Project(노머스)의 **프로젝트 지침**에 [work-session-prompt.md](work-session-prompt.md)의 코드 블록 전체를 붙여넣는다.
2. 이후 그 Project의 모든 대화가 PM 실무 모드로 동작하고, 기록할 만한 순간에 "📌 커리어 기록 후보"를 제안한다.
3. 프로젝트 지침을 쓰지 않는 일반 대화에서는 아래 명령어 A 앞에 work-session-prompt를 한 번 붙여넣고 시작한다.

---

## 2. 붙여넣기용 명령어

### A. 오늘 업무 반영 (업무 대화 끝날 때)
```
GitHub 레포 PUPBAEK/career-notes를 쓰기 권한으로 연결해줘.
레포의 CLAUDE.md 규칙대로, 이 대화에서 진행한 내용을 companies/knowmerce/ 아래 해당 프로젝트 파일에 반영해줘.
- 내가 직접 한 것과 팀이 한 것 구분
- 확정 안 된 결과는 [확인 필요]
- 커밋 전에 추가·수정 문장 요약 먼저 보여줘
```

### B. 새 프로젝트 시작
```
career-notes 레포 연결해서 companies/knowmerce/에 새 프로젝트 파일을 만들어줘.
프로젝트명: <이름> / 파일명: <kebab-case>.md
지금까지 이 대화에서 나온 배경·내 역할·범위로 초안 잡고, 폴더 README 프로젝트 목록에도 추가해줘.
```

### C. 결과 확정 ([확인 필요] 해소)
```
career-notes 레포 연결해서 companies/knowmerce/<파일>.md의 [확인 필요] 항목 중
"<항목>"을 "<확정된 결과>"로 바꾸고, 회사 README의 대표 성과·이력서 문장에도 반영해줘.
```

### D. 이력서·자소서 작업 (커리어 대화에서)
```
career-notes 레포 최신본을 연결해서 읽고 작업해줘. CLAUDE.md 규칙을 따르고,
[확인 필요] 항목은 쓰지 마. 결과물은 applications/<회사>-<직무>.md로 저장하고 커밋해줘.
작업: <예: KREAM Pay 결제 기획 자소서 4문항 / 사람인 경력기술서 노머스 항목 갱신>
```

### E. 정기 점검 (월 1회 권장)
```
career-notes 레포 연결해서 전체 점검해줘.
- 남아 있는 [확인 필요] 목록
- 실명·금액·내부 식별값 같은 규칙 위반
- 회사 README 이력서 문장과 프로젝트 파일 사이 불일치
수정은 하지 말고 목록만 보여줘.
```

## 3. 이력서까지 가는 흐름

```
업무 대화 ──(A)──▶ 프로젝트 파일 ──▶ 회사 README ──(D)──▶ applications/ ──▶ 사람인 · 포트폴리오 · 자소서
             사실 기록 (STAR, 결정, 산출물)   요약 (대표 성과, 이력서 문장)   공고 맞춤본
```

| 단계 | 파일 | 담는 것 | 기준 |
|---|---|---|---|
| 1. 사실 | `companies/<회사>/<프로젝트>.md` | 배경, 내 역할, 의사결정과 근거, STAR, 산출물, 성과 | 길어도 됨. 빠짐없이 |
| 2. 요약 | `companies/<회사>/README.md` | 한눈에 보기 표, 공통 업무 방식, 이력서 문장 초안 | 프로젝트당 1~2문장 |
| 3. 맞춤 | `applications/<회사>-<직무>.md` | 공고 요건에 맞춰 고른 문장과 자소서 | 공고 키워드 기준으로 선택 |

## 4. 어디에 무엇을 가져다 쓰나

| 제출처 | 가져오는 곳 |
|---|---|
| 사람인 경력기술서 (프로젝트별) | 프로젝트 파일의 `담당 범위` + `성과` |
| 사람인 핵심역량 (45자) | 회사 README `공통 업무 방식`의 역량 이름 + 근거 한 개 |
| 이력서 경력 bullet | 회사 README `이력서 문장 초안` |
| 자소서 "문제 해결·갈등" 문항 | 프로젝트 파일의 `문제 해결 사례(STAR)` |
| 자소서 "지원 동기·관심 분야" | 프로젝트 파일의 `배경` + 산출물(테크블로그·브런치 등 외부 활동) |
| 포트폴리오 딥다이브 | `핵심 의사결정` 표(A안/B안) + STAR + 산출물 |
| 면접 답변 | 프로젝트 파일의 `어필 포인트` + 회고 |
| AI 활용 문항 | `side-projects/README.md` 역할 분담·검증 장치 |

## 5. 이력서 문장 공식

**[무엇을] + [어떻게 — 내 판단·방법] + [결과 — 수치 또는 상태]**

| 약한 문장 | 강한 문장 |
|---|---|
| 이모티콘 정산 기획 담당 | 메시지 단일 정산 체계에 이모티콘 정산 편입 — 계좌 단위 선급금 공유로 인한 이중 차감 위험을 계좌당 큐 구조로 해결 |
| PayPay 결제 연동 기획 | SBPS 스펙 원문 검토로 PayPay 환불 정책 오류 2건을 개발 착수 전 정정 |
| CMS 구조 개선 | 컴포넌트 기반 템플릿 전환으로 퍼블리싱·개발 리드타임 5~8일 → 1~3일 단축 |

- 수치가 없으면 상태로 끝낸다: "개발 전 차단", "운영 반영", "원인 규명 및 수정 방향 수립"
- 팀 성과는 "내가 한 부분"이 드러나게: "~를 설계해", "~를 발견해"

---

## 6. 제출 전 체크리스트

- [ ] `[확인 필요]` 항목이 제출본에 남아 있지 않다
- [ ] 역할 범위를 부풀리지 않았다 (예: 갤럭시샵 "구축 PM"이 아니라 "결제·주문·환불 파트 PM")
- [ ] 동료·거래처 실명, 금액 상세, 내부 시스템 이름이 없다
- [ ] 같은 사실이 이력서·포트폴리오·자소서에서 같은 숫자로 쓰였다
- [ ] 면접에서 질문받으면 프로젝트 파일 수준까지 설명할 수 있다
